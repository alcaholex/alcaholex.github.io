# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — dev server at http://localhost:3000
- `npm run build` — static export to `out/` (`output: 'export'` in next.config.mjs)
- `npm run lint` — ESLint (eslint-config-next)

A dev server is usually already running on port 3000 (the developer's own); `next dev` serves current source, so browser checks should reuse it rather than spawning another instance — only start a server if port 3000 is actually closed, and stop it as soon as verification is done. Separately, Claude Code on Windows flashes an empty console window for EVERY spawned command (known upstream bug, anthropics/claude-code#66540 — subprocesses spawn without `windowsHide`); nothing in this repo fixes that, but batching shell commands and avoiding redundant runs keeps the flashing down.

There are no tests. Deployment is automatic: pushing to `main` runs `.github/workflows/nextjs.yml`, which builds and publishes `out/` to GitHub Pages and also FTP-syncs it to Infomaniak hosting (alex.li; secrets `FTP_SERVER`/`FTP_USERNAME`/`FTP_PASSWORD`/`FTP_SERVER_DIR`). The Infomaniak host only speaks plain FTP (FTPS fails with "security scheme is not implemented"), its Starter plan caps storage at 10 MB (the export is ~6 MB), and a failed FTP step fails the build job, which also blocks the Pages deploy. `public/.htaccess` routes 404s to the exported `404.html`. Do not add a `static_site_generator` input to the configure-pages action in that workflow — it generates a competing `next.config.js` that shadows ours and breaks the export (see the comment in the workflow). On Windows, `npm run build` fails with `EBUSY` if any shell's working directory is inside `out/` — the export starts by deleting it.

## What this is

A single-page portfolio site: Next.js 15 App Router, plain JavaScript (no TypeScript), Tailwind CSS v4 (configured in CSS via `@theme` in `src/app/globals.css`, no tailwind.config file). Everything is a client component; the only page is `src/app/page.js`, composed of full-screen sections (`section-1` hero … `section-4` art) that the navbar scrolls between.

## Architecture

Several cross-cutting systems interact — most components touch more than one of them. Source comments are deliberately sparse; the whys live here.

**Title snapshots (no loading screen).** There is no loading overlay — the site is visible and scrollable immediately. Instead, each 3D title mounts a `TitleSnapshot` (`TitleSnapshot.js`): a static webp of the rendered title (`public/titles/{name,projects,art}-{light,dark}.webp`) absolutely positioned over the canvas (`z-50` above the canvas's `z-40`, `pointer-events-none`), which fades out over 400ms once ALL three scenes report ready (`useAllAssetsLoaded` — a lone early scene popping in reads as a glitch, so the swap is synchronized). `LoadingGate.js` survives as the plumbing only: a context provider where scenes call `useAssetReady(id)` (ids `'name'`/`'projects'`/`'art'`, fired by `Warmup` post-compile so the swap never lands on first-frame jank) and snapshots read `useAssetLoaded(id)`. There is no timeout — a scene that never loads just keeps its snapshot, which is the right fallback. Positioning: all three scenes render the title at a fixed fraction of *viewport width* (`Center scale={viewport.width/8.5}`), centered in the window (LensShift), so the snapshot geometry in `TitleSnapshot.js` — width in vw, center in %, measured at 1440×900 — tracks every viewport size and both breakpoints. The snapshots are a MATCHED set with the scenes: changing a GLB, AO map, `TitleMaterial` color, camera, or `Center` scale requires re-capturing all six images — run `node scripts/capture-titles.mjs [port]` against a dev server; it logs the GEOM lines to sync into `TitleSnapshot.js` (each snapshot div carries `data-snapshot={id}`, which is also the script's readiness signal). Both theme variants are plain `<img>`s toggled with `dark:` classes — the hidden one still downloads, which is fine at ~115KB total for all six. Load pipeline (anti-jank staging, profiled at 4× CPU throttle): the three scene components are `next/dynamic` `ssr: false` imports at their usage sites (page.js for the hero, Projects.js/Art.js for theirs) so three.js lives in an async chunk and hydration stays light (First Load JS 378kB → 121kB) — which is exactly why the snapshots and the `relative w-full h-screen` wrapper divs live in the PARENTS, not the scene components: `ssr: false` drops a component from the prerendered HTML, so anything that must paint instantly (the snapshot) or hold layout (the wrapper) has to stay outside. Inside each scene `useDeferredMount` (0/250/500ms, then rAF + timeout so a paint separates it from whatever ran before) delays `<Canvas>` creation so each WebGL context + GLB parse gets its own task, and `Warmup` serializes `compileAsync` + first-frame across canvases via a module-level promise queue — concurrent warmups coalesce into one long task. Do NOT re-add module-level `useGLTF.preload(...)` in the scene files: the head preloads (layout.js) already have the bytes in HTTP cache, and drei's preload starts an unscheduled GLTF parse the moment the network resolves, outside the stagger. Net effect: no main-thread task over ~250ms during load (baseline had a 469ms hydration+three-contexts block). NOTE: there is no guaranteed pre-entry gesture, so `sfx.unlock()` first fires on the visitor's first real interaction (hero drag, nav click, station tap — all already call it); audio before that point is impossible by browser policy. The Fascinate font (layout.js) was the old loading screen's CONTINUE label face and is currently unreferenced.

**Scrolling.** Native scroll only (a Lenis smooth-scroll layer was removed; see git history). Programmatic jumps use `window.scrollTo({ behavior: 'smooth' })`/`scrollIntoView`. Two hard-won constraints govern anything built on top:

- *There is no "is a smooth scroll in flight?" signal* (Lenis's `isScrolling` is gone, and the platform offers none). The stand-in is `navScroll.js`, a module-level flag with a self-clearing deadline: **every** programmatic smooth scroll must call `navScroll.mark()` (navbar jumps, hash restore, ScrollHint's descend all do) — a new scroll site that forgets it reintroduces a nasty bug where `SlideInSection`'s snap fires mid-travel and, because a second `scrollTo` *cancels* an in-flight smooth scroll, hijacks the navigation and drags the visitor back where they came from.
- *Idle-detection timers must out-wait smooth-scroll frame gaps.* `SNAP_IDLE_MS` is 120ms because scroll events during a native smooth animation can gap longer than the old 20ms, making "scrolling stopped" fire mid-animation. The snap also re-queues while `navScroll.active`.

`SlideInSection` uses the flag to tell a passing navigation from a user swipe when deciding whether to commit a section. Modals (metro-map station, art lightbox) lock scroll by setting inline `overflow: hidden` on `<html>` for their lifetime. `html`/`body` use `overflow-x: clip` (not `hidden`) so neither becomes a horizontal scroll container when swipes or station drags overflow.

**Hero drag on touch devices.** On `pointer: coarse` devices, `ThreeDName.js` binds its OrbitControls not to the canvas but to an invisible overlay (`[data-title-drag]`) that a per-frame tracker keeps positioned/sized to the title's screen-projected bounds — so touches on white space hit the canvas and scroll the page natively, while drags starting on the title rotate it. Constraints that hold this together: three-stdlib's `connect()` stamps `touch-action: none` on whatever element controls bind to (which is exactly what used to make the whole hero swallow mobile scrolling); the overlay is sized outright rather than full-screen with a `clip-path` hit-region because WebKit's clip-path hit-testing is unreliable; since OrbitControls scales rotation by the bound element's `clientHeight`, `rotateSpeed` is rescaled per frame by overlay/canvas height so the feel matches canvas binding; and the tracker writes styles imperatively from `useFrame` — routing them through React state would re-render every frame during drags. While a title drag is active the page scroll locks (modal-style inline `overflow: hidden` on `<html>`, released on the controls' `end` event) so a second finger can't scroll the page out from under the drag; the lock is overlay-path only because on desktop the vanishing scrollbar would reflow the page mid-drag. iOS ignores `touch-action: none` in enough cases (top-of-page rubber-band especially) that the overlay also carries a non-passive `touchmove` `preventDefault` — the one scroll-blocking mechanism WebKit always honors — and the drag-time lock adds the same blocker window-wide. Testing caveat learned the hard way: headless Chrome with touch emulation (CDP `dispatchTouchEvent`, `pointer: coarse` matching) validates hit-targeting and scroll wiring but proves nothing about WebKit — this feature passed every emulated check while a real iPhone scrolled mid-drag. Anything touching `touch-action`, clip-path hit-testing, or scroll locking needs an on-device iOS pass before calling it done. `DragHint` dismissal accepts drags starting on either the canvas or the overlay.

**3D scenes.** Three R3F canvases (`ThreeDName.js` hero, `ProjectsTitle.js`, `ArtTitle.js`) each load a GLB from `public/models/` (Blender sources in `blender/`). Shared performance pattern: `frameloop` is toggled `'always'`/`'never'` by visibility so off-screen canvases don't render, and `Warmup.js` precompiles shaders (`gl.compileAsync`) before calling the scene's ready callback so the snapshot swap never lands on first-frame jank (and serializes warmups across canvases — see "Title snapshots"). The hero canvas is 150vh on desktop while the window is 100vh, so `LensShift` writes a vertical off-center term into the projection matrix every frame to center the name in the *window*; the other two canvases are 1:1 and don't need it. The GLBs are preloaded from the HTML head (`layout.js`, `ReactDOM.preload` with `crossOrigin: "anonymous"` — the mode must match three's FileLoader fetch or the browser downloads every model twice).

**Title materials.** All three titles wear `TitleMaterial.js`: one flat unlit `meshBasicMaterial` color per theme, `toneMapped` off so the colors keep their CSS values (ACES tone mapping otherwise caps pure white at ~85% gray), and a baked AO map (`public/ao/{model}-ao.png`, strength via `aoMapIntensity`) multiplied over the flat color. There is deliberately no lighting, environment, or adaptive-quality tiering — a previous transmission-glass version with runtime degradation was removed for a single level of detail (see git history around `0d39a11` if it's ever wanted back). Texture gotchas that already bit once: textures hand-loaded onto glTF geometry need `flipY = false` set *before* the first GPU upload (drei's `useTexture` force-uploads before its onLoad callback runs, so it can't do this — hence the hand-rolled loader), and AO maps sample linear, never sRGB.

**Blender → site asset pipeline.** Each `blender/*.blend` keeps the editable FONT object *plus* a converted, Smart-UV-unwrapped mesh copy — the copy is what exports (text objects can't unwrap; convert first). A model's GLB and its AO PNG are a **matched pair**: changing the unwrap requires re-baking *and* re-exporting together, then syncing both into `public/` (`public/models/{model}.glb`, `public/ao/{model}-ao.png` — bakes saved in `blender/` don't reach the site until copied). A stale or mismatched pair renders as black patches/stripes (faces sampling the bake's background); alignment is provable by sampling the PNG at every GLB UV — zero vertices should land on background. Export gotchas: the glTF exporter includes objects by *viewport* visibility (hiding from render isn't enough — use Selected Objects), baking is Cycles-only (Eevee has no bake system), and bake Margin below ~32px at 1024² shows as lines along UV island seams. When verifying bakes via headless screenshots, render at `deviceScaleFactor: 2` — at small sizes mipmaps average misaligned texels into plausible-looking shading — and note Puppeteer `screenshot({clip})` coordinates are document-relative, not viewport-relative.

**Perf testing.** `/perf-test` (`.claude/skills/perf-test/`) builds the site and drives a real browser through the visitor flow under CPU/network/GPU throttling profiles, reporting load times and FPS.

**Sound.** `src/components/sound.js` synthesizes every effect with Web Audio at call time — there are no audio files. The AudioContext is created/resumed only from gesture-bound calls (browsers refuse audio before a user gesture); a looping silent `<audio>` element ("keeper") keeps iOS from muting Web Audio via the ringer switch — a *playing* media element flips the iOS session to the playback category — and is re-armed per gesture. UI components call `sfx.chord(...)`, `sfx.spin(...)`, etc. fire-and-forget. Musical design: chord tables are just-intonation ratios on an A root, not frequencies; `NAV_CHORDS` is an I–IV–V–I cadence, and the opener pools are all diatonic in A leaning away from the root so the fixed low closers (`labelsOff`, `boardClose`, `dismiss`) resolve whichever opener played. The hover tick fires for `pointerType === 'mouse'` only — on touch, `pointerover` is part of the tap and would double its sound.

**Metro map.** `FlowTimeline.js` draws the about-section timeline as a metro map with spring-physics draggable stations. The map is edited via the data tables at the top of the file — stations (`id`, `year`, `title`, `body`, optional `labelSide`/`labelNudge`/`shift`) and lines (ordered station ids; `horizontal: true` = crosstown row); the layout itself is generated, with `VARIANCE` (0–100) adding seeded track jogs — reroll `JOG_SEED` to reshuffle. Terminal arrows live inside the station div so they ride along with drags, and aim along the track's real first piece (not at the neighbor station) so doglegs don't misalign them. Station drags rely on pointer capture; `pointercancel`/`lostpointercapture` both release the drag or a swallowed pointerup (edge gestures, alt-tab) leaves a station stuck at full stretch. No `preventDefault` on station pointerdown — it would suppress compatibility mouse events. A text selection spanning a station turns its drag into a native drag-of-selection whose `pointercancel` kills ours, so pointerdown clears any non-collapsed selection and stations `preventDefault` on `dragstart`. Stations use `touch-action: none` so the page can't scroll out from under a drag. Modal close paths (X, backdrop, Escape) all converge on `dismiss` for the fade + sfx.

**Theming.** Dark mode is a `dark` class on `<html>` (Tailwind v4 `@custom-variant` in globals.css), toggled in `Navbar.js`, persisted to `localStorage.theme`, and restored before first paint by an inline script in `layout.js` (hence `suppressHydrationWarning`). Theme switches add a transient `.theme-fading` class that cross-fades colors site-wide (`!important` so it beats inline styles). Semantic CSS vars (`--ink`, `--paper`) exist for the metro-map SVG. Sections declare `data-navbar-theme` for the navbar's color handling. Components outside React state that need the theme (e.g. `TitleMaterial`) watch the class with a MutationObserver. To retheme site-wide, override `--color-gray-*` in an `@theme` block in globals.css and keep `--background`, `--ink`/`--paper`, and the `TitleMaterial` colors in lockstep — see git history around Aug 2026 for full worked examples (warm palettes and an "INTERCHANGE" transit design system). The background lives in THREE coupled places that must change together: `--background` in `globals.css` `:root`, the `--color-gray-50` override in the `@theme` block (sections, the loading gate, and metro-map labels paint with `bg-gray-50 dark:bg-gray-950` utilities), and the light `TitleMaterial` color, tinted toward the same hue so the 3D titles don't clash with the page. To retheme ONE mode only, scope the `--color-gray-*` overrides inside the `.dark` block (or `:root` for light) instead of `@theme` — v4 utilities resolve `var(--color-gray-*)` per element, so the redefined custom properties only reach elements under that class; keep `--paper` in lockstep with gray-900, `--ink` with gray-100, and mind that a dark `TitleMaterial` color at or below the new page value makes the titles vanish (the stock relationship is title two ramp steps above the page).

**Fonts.** Body text is local-first Helvetica Neue (licensed — must come from the visitor's machine) falling through Arial to Arimo, a metric-compatible webfont backstop, so line breaks never move whichever loads; Montserrat is navbar-only (`--font-nav`); Fascinate (local TTF, `display: "block"`) was the loading-screen CONTINUE button's face; the button is gone (auto-reveal gate) so it's currently unreferenced but still wired in layout.js for reuse.

## Conventions

- Source comments are kept to a minimum: only terse notes on constraints that would cause a bug if violated survive in code. Everything else worth knowing belongs in this file — when you learn something non-obvious, add it here, not as a code comment.
- UI copy is lowercase by design ("i'm a high school student…", nav labels).
- Expanding panels animate `grid-template-rows: 0fr → 1fr` (the animatable stand-in for `height: auto`); `<img>` tags are guarded (`project.image &&`) because a src-less img renders a broken-image icon.
